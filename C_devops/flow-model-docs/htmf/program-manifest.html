Program manifest

A program manifest is the shopping label for a runnable variant: which flow boots, which modules mount, which feature tokens it implements, and (optionally) which features it explicitly does not include.

Canonical JSON Schema: C_devops/flow-model-docs/schema/program_manifest.schema.json (hostpark mirror: publish via identity when pinned).

Why manifests exist

  • Viewport / launch_index can show what a program imps without opening every flow.
  • Baseline flows stay thin — excluded features live in feature_excludes on other manifests.
  • artifact_contracts document standard I/O so variants test in isolation and compose later.

Required fields

FieldRole
idStable program id (tipunch:program:pm_field_v2)
labelHuman name — name the sandwich, not the missing ingredient
whyWho + journey + wedge
flowLogical route to flow JSON
launchLogical route to launch fragment

Feature shopping

  • feature_imps — capability tokens this program implements
  • feature_excludes — optional explicit non-goals

Same token across manifests = same capability for merge / compose-all. A future suite program uses compose_from to union member manifests after contracts validate — not by bloating the PM wedge flow.

Layers

layers maps UX spectrum (L0–Ln) to artifact routes. Swap L2 (photo bin module) without renaming L4 flow when registry API stays stable. See ux-spectrum.

Artifact contracts

{
  "artifact": "modules/tipunch_registry.js",
  "kind": "module",
  "provides": ["registry.getJob", "registry.jobStats"],
  "requires": ["navi.storage.tip", "navi.storage.bin"],
  "consumes": ["schema/punch_item"],
  "emits": ["tipunch:job:*"]
}

Alternate apps (sub portal vs PM walk) use different flows + manifests but require the same registry provides tokens.

Project convention

<project>/
  programs/*.json
  data/launch_index.json
  flow/*.json
  launch/*.html            # bootstrap bookmarks (not flow screens)
  ui/*.html                # flow route screens only

Example: opry/devops/ti_punch/programs/ on hostpark.
