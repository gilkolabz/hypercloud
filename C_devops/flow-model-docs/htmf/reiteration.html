Reiteration (after shopping)

How flow-model devops takes new product ideas once a runnable spine exists — without restarting greenfield shopping, and without stuffing every idea into one launch.

Related: variants (shopping), composition (programs / networks), ux-spectrum (layers), devops-goals.

Stages (not numbered “phases”)

Prefer layers (L0–Ln) for artifact placement. For devops process, name stages plainly:

StageWhat you do
ShoppingPick / declare programs and feature tokens; compare launches; keep wedge thin
SpineShip a showable journey (entry → real outcomes)
ReiterationClient or operator survey → brief → sorted features on spectrum → build order
Network growthAdd sibling programs (roles, canvases) that share schemas; do not cross every feature into every launch

Older “phase N” language in project notes can map here; paradigm docs use stages + layers.

Client survey → brief

  1. Capture — Raw survey / transcript. Keep it.
  2. Brief — One project doc that sorts the transcript into features: user, job-to-be-done, spectrum level, acceptance, not-this, priority. State locked decisions.
  3. Paradigm check — New composition rules (e.g. program networks) go into flow-model docs generically — not as a product name inside paradigm pages.
  4. Build — Only after human says go. Brief stays plan until then.

The brief is the working contract for reiteration. Shopping indexes (launch_index, manifests) stay the contract for what already runs.

One spine, many programs

Reiteration often asks for breadth (portfolio, GIS, role portals, checklists) and a sharp field journey.

  • Shared facts — L0/L1 schemas and registry APIs intersect so local-first and hostpark stay coherent.
  • Split journeys — Different programs + launches for different roles or canvases.
  • No silent mega-Manager — New surfaces get routes/programs; they do not all land in one policy file by default.

If breadth needs a parent canvas, declare a program network — members remain independently launchable.

Feature shape (brief template)

For each feature: user / role; job to be done; where it lives (screens · modules · spectrum L…); acceptance; not this; priority; optional survey source. Group into a few bets; collapse duplicates.

Anti-patterns

  • Treating reiteration as shopping that discards the spine
  • Putting every survey wish on the primary field launch
  • “Dashboard” that is a second product with no program boundary
  • AI as decoration instead of a named assist on a capture or follow-up path
  • Updating only a product folder when the composition rule itself changed
