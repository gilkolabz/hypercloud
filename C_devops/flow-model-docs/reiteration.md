# Reiteration (after shopping)

How flow-model devops takes **new product ideas** once a runnable spine exists — without restarting greenfield shopping, and without stuffing every idea into one launch.

Related: [variants.md](variants.md) (shopping), [composition.md](composition.md) (programs / networks), [ux-spectrum.md](ux-spectrum.md) (layers), [devops-goals.md](devops-goals.md) (why-strings).

## Stages (not numbered “phases”)

Prefer **layers (L0–Ln)** for artifact placement. For **devops process**, name stages plainly:

| Stage | What you do |
|-------|-------------|
| **Shopping** | Pick / declare programs and feature tokens; compare launches; keep wedge thin |
| **Spine** | Ship a showable journey (entry → real outcomes) |
| **Reiteration** | Client or operator survey → **brief** → sorted features on spectrum → build order |
| **Network growth** | Add sibling programs (roles, canvases) that share schemas; do not cross every feature into every launch |

Older “phase N” language in project notes can map here; paradigm docs use stages + layers.

## Client survey → brief

1. **Capture** — Raw survey / transcript (voice of prospect or operator). Keep it.
2. **Brief** — One project doc that sorts the transcript into features: user, job-to-be-done, spectrum level, acceptance, not-this, priority. State locked decisions.
3. **Paradigm check** — Anything that needs a new composition rule (e.g. program networks) goes into **flow-model** docs generically — not as a product name inside paradigm pages.
4. **Build** — Only after human says go. Brief stays plan until then.

The brief is the working contract between human and assistant for reiteration. Shopping indexes (`launch_index`, manifests) stay the contract for **what already runs**.

## One spine, many programs

Reiteration often asks for breadth (portfolio, GIS, role portals, checklists) **and** a sharp field journey.

Rule:

- **Shared facts** — L0/L1 schemas and registry APIs intersect so local-first and hostpark stay coherent.
- **Split journeys** — Different **programs + launches** for different roles or canvases (already: field walk vs inbox vs suite).
- **No silent mega-Manager** — New surfaces get routes/programs; they do not all land in one policy file by default.

If breadth needs a parent canvas, declare a **program network** ([composition.md](composition.md)) — members remain independently launchable.

## Feature shape (brief template)

For each feature:

- User / role  
- Job to be done  
- Where it lives (screens · modules · **spectrum L…**)  
- Acceptance (demoable)  
- Not this  
- Priority (must / should / later)  
- Survey source (optional)

Group features into a few **bets**; collapse duplicate survey bullets.

## Anti-patterns

- Treating reiteration as a new shopping exercise that discards the spine  
- Putting every survey wish on the primary field launch  
- “Dashboard” that is really a second product with no program boundary  
- AI as decoration instead of a named assist on a capture or follow-up path  
- Updating only a product folder when the **composition rule** itself changed
