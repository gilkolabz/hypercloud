First extraction (2026-07-01).

Navi runtime semantics

callin, not stdin

The programmatic text-stream interface is callin, not stdin.

  • Modules expose commands; the runtime wires callin listeners automatically (new register pattern).
  • Manual: navi.on('callin', â€¦) and navi("command args").
  • Aligns with the shell runtime and navi_modules_guide.

In devguides, say "callin/commands" or "programmatic API via commands". Avoid "stdin" in new docs.

Namespaced callin commands

Each project's callin surface should use one top-level command (project name), with operations as subcommands. Do not use bare verbs like lookup or list that collide across modules.

Example:


    clinicnotes start
    clinicnotes lookup 12345
  • The callin module (e.g. clinicnotes_init) owns the namespaced commands object.
  • Logic modules (e.g. clinicnotes_registry) expose programmatic API only. No top-level commands unless the command name itself is namespaced.

Other modules call logic via navi.mod.*.registry â€” not ambiguous callin strings.

onUnmount vs runtime cleanup

navi.unmount(module) automatically removes callin listeners registered from commands and deletes navi.mod[name]. Modules must not manually detach callin in onUnmount.

onUnmount is for module-owned resources the runtime does not know about: event listeners, DOM nodes, styles, observers, timers, and cascade unmounts (e.g. init unmounts registry it mounted).

A callout-only onUnmount is unnecessary for command-only modules.

Composable screen capabilities (not folder variants)

Small features on a shared screen role should not fork folder HTML or multiply layout variants. Use one host per screen role, optional flow meta, and a module or route for behavior.

Decision tree

QuestionIf yesIf no
Does the whole screen layout change?New ui/*.html + flow artifact + launch_*.html (e.g. pile vs page-turn folder)Keep existing host
Optional behavior on a shared screen?Flow meta flag + module and/or new route key (e.g. settings sections, virtual edit)â€”

Example: virtual record Edit (clinicnotes)

  • Wrong layer: folder_virtual_records_with_edit_button.html â€” edit is not on the folder list; all folder variants already call mgr.openDoc() â†’ doc_sheet.
  • Right layer:

    • - Read host: doc_sheet.html â€” Edit button in toolbar (top-right) - Write host: doc_edit.html â€” new flow route doc_edit - Registry: updateVirtualDoc, deleteVirtualDoc; prior snapshot kept on the owner record - Enablement: flow meta.virtual_record_actions: ["edit","delete"] + clinic pref virtualEditEnabled - Manager: openDocEdit(), canEditVirtual() â€” mirrors settings return pattern without duplicating folder UIs

Devops bookkeeping (minimum for any composable feature)

  1. One sentence in project devguide.md glossary
  2. One checklist line in launch_linker.html
  3. Flow artifact declares route + meta; GOALS.md notes phase scope
  4. Optional stub flow only when a stakeholder needs the feature off (usually defer)

Shop-for-final-version model: swap modules (parse, view, edit policy) while Manager + registry API stay stable. Folder layout variants stay about how you browse; doc sheet/edit stay about how you read/write one record.

UX variant shopping (clinical products)

For products where the doctor or operator chooses among presentation variants (folder layout, scan pile vs page-turn, entry splash, etc.):

  • Ship **multiple launch_*.html bookmarks + flow artifacts; do not** force a default until the stakeholder picks.
  • Record in GOALS.md which phase closes the decision (e.g. Phase 8 for clinicnotes folder UX).
  • Design ethos: clinical, exact, purposeful â€” color where it aids recognition (digit codes), not blocky mobile-app chrome or wasted nav chrome. Example feedback: page-turn page-index dots work functionally but need a tighter visual treatment.
  • A launch index and a variant graph document the choices. Each path can carry an artifact_type (launch, flow, ui, module, data).

See clinicnotes GOALS Phase 8 UX shopping.

Artifact composition and variant management (clinicnotes retro, 2026-07-07)

This section records a mid-Phase-6 reflection prompted by the project owner. It is the most important refinement so far and should shape future projects from day one.

Why this conversation happened

One clinic product had grown to 51 artifacts across 264 published generations. Snapshot:

CategoryArtifactsFramesNotes
ui screen1783includes 3 forked folder layouts (folder.html 12, folder_scan_pages.html 12, folder_scans_pile.html 9) + a likely-orphan settings_pageturn.html (1)
flow artifact748near-duplicate route+policy maps; adding one route = editing all 7
launch bootstrap918per entryÃ—layout combos; naming drift (scanpages vs flow scan_pages)
module843clinicnotes_manager.js alone = 16 frames (churn magnet)
doc/config/schema/data1072devguide 25, GOALS 18

The owner noticed a real defect in how we got here: variants are forks, not compositions. The three folder screens share ~70% of their code (code row, pet sections, doc list, scan overlay, add chrome) but are hand-maintained monoliths. So a feature added to one (tab + popover, add-pet affordance) does not propagate to the others, and cross-cutting changes (adding pet_add/doc_add routes) fan out into 7 flow files by hand. This is the opposite of the navi_style ethos: resting, composable tools that Manager picks and chooses.

Honest root cause: the assistant introduced "baseline" as an implicit mainline and treated each folder layout as its own ongoing mini-app, folding decisions in prematurely instead of treating each feature as a distinct, composable, independently-versioned concept. The owner never actually chose to fold anything into baseline â€” it was invented for them.

The owner's model (target pattern)

Treat a variant as a composition of feature "concepts," not a fork.

  • Concept artifact = one composable feature unit (e.g. folder_owner_tab, add_popover, add_footers, tick_nav, code_row, pet_sections, scan_overlay, folder_settings, section_order). "page_turn" is itself a concept (a nav treatment), not a whole app.
  • Revisions use _r1, _r2 suffixes. A concept can be revised independently: tick_nav_r2.
  • Variant = a named composition of concepts at chosen revisions, plus rationale. Examples of the owner's naming intuition:

    • - page_turn â†’ next iteration promotes the underlying artifact to page_turn_r1; the old branch stays pinned. - A variant that drops one concept: page_turn_nofoldersettings (branched off the iteration it was made from). - Compose the new base with the tweak: page_turn_r1_nofoldersettings. - Iterate the tweak itself: page_turn_r1_nofoldersettings_r1. - Another dev revises just that concept: nofoldersettings_r2 â†’ page_turn_r1_nofoldersettings_r2. - Variant-of-variant with a distinct handle: nofoldersettings_r2_smileyface â†’ page_turn_nofoldersettings_r2_smileyface.

  • Because listing every concept in the name gets verbose, prefer one of:

    • 1. short concept IDs tacked onto the address (_a3c_b8d_8rf), or 2. (preferred) a variant descriptor data structure â€” each variant gets a wholly unique human name plus a record listing its concepts+revs, a plain-language "why this variant exists" field, base lineage, flow, launch, and status.

  • baseline stays the merge-and-forget mainline: it may overwrite freely, but we must still keep a record of which concepts (and revisions) compose it. Folding into baseline is an explicit owner decision, never assumed by the assistant.

Two layers to build

  1. Record-keeping layer (do first, cheap): a variant/concept registry (extend data/launch_index.json or add data/folder_variants.json + data/concepts.json). Captures composition, revision lineage, rationale, and status. This alone restores coherence and lets us stop losing track â€” even while screens remain forked.
  2. Enforcement layer (bigger refactor): a shared folder builder that assembles a screen from a variant descriptor by mounting enabled concept components, instead of three hand-maintained HTML files. Same idea for flow: generate the 7 flow artifacts from one base + variant deltas rather than editing each. This is what actually stops forking and fan-out edits.

Decisions locked in this conversation

  • Keep Settings in the folder for all variants. The owner used "remove folder settings" only as an example of an easy on-a-whim variant; the point is *we should not have to walk back* â€” distinct launches mean we never must decide. Do not fold decisions in heavily.
  • Page-turn keeps the manilla folder styling (owner-name tab like baseline). The + living top-right (instead of beside the tab as in baseline) is a *good* deliberate shopping difference â€” keep both treatments as distinct concepts.
  • The tick strip nav is approved.
  • parseLayout clarification: a generic record (notes) is intentionally *not* a layout_v1 record; only OCR'd scans produce sections. The section editor appears for layout records in both parse review and doc edit â€” working as intended.

Lesson for future projects

Start with the concept + variant-descriptor model on day one. Every presentational feature is a resting, revisable unit; variants are declared compositions with written rationale; a builder composes them; "baseline" is an explicit, recorded merge target â€” never an assistant default. This is the concrete expression of the separation-of-concerns / composable-tools ethos on the style page, applied to UI/flow artifacts, not just logic modules.

Design convergence â€” registry + builder mechanics (2026-07-07, cont.)

Vocabulary (owner's, adopted): features own artifacts â†’ artifacts compose into instances â†’ instances compose into programs â†’ launches bootstrap a program. Instance always means family-local (e.g. a prebaked folder layout). Program is the layer above instances â€” the full runnable clinic path (journey spine + folder instance, optionally entry). Some instances and programs are variants of others.

Journey under the journey family. Numpad and the shared clinic spine live under the journey family axis; that is fine. A program's compose.journey references the journey flow (e.g. clinicnotes:flow:journey:numpad_direct) until/unless journey gets its own instance records.

Artifacts are multi-kind. A feature is a bundle that can span HTML (slot markup), JS (a behavior module), flow meta (route reachability), CSS, schema, and data. The instance wires each kind to its place: HTML â†’ a named slot, JS â†’ Manager registration, flow meta â†’ merged into the route map. This is not new machinery â€” Manager already composes the *logic* artifacts at runtime (parse / virtual_view / edit-policy); the builder just extends "pick and place" to the *view* layer.

Addressing â€” three distinct concepts, kept separate:

  • Reference token (canonical, in instance records): feature@rev, e.g. add_affordance@topright_r1.
  • Catalog nesting (registry tree): add_affordance.topright_r1.
  • Hostpark ib: the route readers fetch, e.g. fragments/add_affordance/topright.html. One generation of that route is ib^gib.

Two version axes, meaning different things:

  • Revision (_r1, _r2) = a distinct hostpark path / parallel branch. Lets a variant *pin* topright_r1 forever while topright_r2 exists alongside. (Frames cannot do this â€” they are linear per path.)
  • Frames = micro-history *within* one revision (typo fixes, tweaks).

So: feature = stable namespace â†’ artifact-revision = distinct branchable path â†’ frames = that path's edit history. The registry is itself a framed artifact, so a third party can reconstruct the composition graph by querying paths (same principle as launch_linker / launch_graph).

Slot contract (composition mechanism). Prior art: named slots / content projection (Web Components , Vue slots, transclusion, static-site partials). Our version does it without a framework, over plain surfed fragments:

  • Host template exposes named slots. Day-one form: string markers (trivial, inspectable â€” this is #include, not a slot engine; DOM slotting via jsdom is a later nicety).
  • Fragment declares its target: data-slot="folder_top_lip" + data-artifact="add_affordance@topright_r1". Prefer data-* over name= (collision-safe; name has form semantics).
  • Builder matches by stable slot id only. Two artifacts claiming one slot â†’ builder errors loudly (explicit, never silent collision).
  • Scope each feature's CSS under its data-artifact selector to prevent layout bleed.
  • Machine contract vs authorial color: the stable slot id + token is what the builder keys on; verbose/human names, authorship (..._dropdown_by_mr_boaz), and descriptions live in description/author fields. Corollary (owner's): the feature (idea) is the translator; individual artifacts may be parochial to the instance context and need not be universally portable. This collapses the combinatorial-collision worry â€” the builder only reconciles stable ids within a family.

Builder â€” flavor A (build-time generate), deliberately dumb first:

  1. Read instance record â†’ resolve each feature@rev token to its fragment.
  2. Load host template with string slot markers.
  3. Inject each fragment's markup at its slot; concatenate its scoped CSS; note the Manager method its JS needs.
  4. Apply the variant delta (remove / replace / add).
  5. Emit ui/.html with a provenance header comment (), plus its flow JSON and launch from templates; upload via existing script.

Doing A first also de-risks B (run-time slot-mount): A forces us to define the slot contracts, which B reuses. B has little added value for clinicnotes specifically, so it's deferred but not foreclosed.

Fork rule (resolves the "generated output" question). A generated ui/*.html is a *build product*. Hand-editing it silently forks it from its recipe â€” the exact drift disease. Forks are allowed, but a hand-edited output must be promoted to a declared instance/artifact in the registry, never left as silent drift. Forks can exist; they cannot steer the ethos or hide.

Safety strategy â€” do not lose progress. The builder proves itself by producing the next needed change (reintroduce the owner-name tab on page-turn), *not* by dismantling the three working forks. The existing forks stay declared in the registry as hand-authored instances until builder-generated equivalents are validated, then we cut over deliberately.

Drift evidence (why this was worth stopping for). Reading the three folder files back-to-back, the divergence is accumulated drift, not considered variation:

  • folder.html (baseline): code-row digit chips, fused + dropdown (Add pet / Add document), pet management (add pet, per-pet "Add details"), section-order pref (docs_first).
  • folder_scans_pile.html: no code-row, no pet management, no section-order.
  • folder_scan_pages.html: no owner tab, no code-row.

    • Two of the three are simply older/less complete; good features never propagated. A feature matrix would surface these gaps instantly; a builder restores parity near-free instead of hand-porting.

Canonical addressing doctrine (2026-07-08, strict turn)

The stronger model is:

  • Integral typed id is canonical and authored. clinicnotes is the product namespace; folder is the explicit subfamily axis for this registry:

    • - clinicnotes:fragment:folder:add_affordance@topright_r1 - clinicnotes:host:folder:layout_pageturn@r1 - clinicnotes:instance:folder:page_turn_owntab - clinicnotes:flow:folder:page_turn_owntab - clinicnotes:launch:folder:page_turn_owntab - clinicnotes:program:folder_page_turn_owntab

  • Derived branch route is mechanical, never separately authored except as a rare escape hatch. Examples under the current physical root:

    • - clinicnotes:fragment:folder:add_affordance@topright_r1 -> opry/devops/clinicnotes/fragments/folder/add_affordance@topright_r1.html - clinicnotes:host:folder:layout_pageturn@r1 -> opry/devops/clinicnotes/fragments/folder/layout_pageturn@r1.html - clinicnotes:instance:folder:page_turn_owntab -> opry/devops/clinicnotes/ui/folder_page_turn_owntab.html - clinicnotes:flow:folder:page_turn_owntab -> opry/devops/clinicnotes/flow/flow_folder_page_turn_owntab.json - clinicnotes:launch:folder:page_turn_owntab -> opry/devops/clinicnotes/ui/launch_folder_page_turn_owntab.html

  • Generation address is ib^gib: the branch route plus the content hash of that generation.
  • Surf URL is /{ib} on the current host. The ib is the route. There is no extra prefix.

This resolves the earlier route confusion cleanly:

  • Session and config store the ib, such as opry/devops/clinicnotes/ui/numpad.html.
  • Flow routes store the surf URL for that ib: /opry/devops/clinicnotes/ui/numpad.html.

So there are still two forms, but they are now understood as integral/logical vs transport/surf, not as accidental inconsistency.

Strict policy adopted:

  1. Do not author separate storage-route fields when the route can be derived from the typed id.
  2. Publish everything as first-class routes eventually: fragments, hosts, instances, flows, launches. This preserves lossless devops history and enables future flavor-B runtime composition.
  3. Generated outputs are build products, but their ids are still first-class (instance, flow, launch) and can themselves accumulate hostpark frames.
  4. variant_of uses typed instance ids, not registry map keys. Example: clinicnotes:instance:folder:page_turn, not folder_page_turn.
  5. Product-level map: data/artifacts.json is the canonical catalog for the entire clinicnotes project (all families). data/programs.json records programs (compose journey/entry/folder). data/launch_index.json points clinic launches at program_id. Folder composition detail remains in folder_concepts.json + folder_instances.json + folder_flow_base.json.

Programs layer (2026-07-08)

Almost every clinic launch composes journey (numpad spine) + folder (+ sometimes entry splash). That composition is explicit now:

  • Instance = one family's prebaked contribution (clinicnotes:instance:folder:page_turn).
  • Program = composed runtime across families (clinicnotes:program:folder_page_turn_owntab).
  • Launch = bootstrap bookmark for a program (clinicnotes:launch:folder:page_turn_owntab).

programs.json compose keys name the family axis (journey, entry, folder) and hold typed ids (flow for journey spine, instance for folder/entry screens). Devops surfaces (linker, graph) have no program.

Flow: browser shell, surf, flow artifacts, Manager

Flow is how the user moves through a product â€” which screen comes next and what context carries forward. On foobarch this is expressed through the navi shell plus navi.storage, not a bloated flow.js UI module.

See navi shell.

Browser shell and in-app navigation

  • The top shell loads navi_shell.js once. navi.storage, init_script, and mounted modules persist while body content changes.
  • Direct entry to a path: foobarch SSR may still bootstrap the first screen with an HTMX hx-get element in the shell body.
  • Entry at /: empty body; init_script may seed an HTMX element to a default route and call htmx.process.
  • Step-to-step movement inside a project uses surf, not HTMX. navi.mod.surf.surf(url) fetches the route, parses HTML into a template, and replaceChildren on document.body. No hx-get flicker.
  • Hostparked HTML fragments are the payload surf loads. Navi stays in the shell window.
  • Prefer fragments without id. Use data-part and name (and hx-target on that name). Ids are document-global and collide when a swap duplicates a stage.
  • A bookmark or a direct route is the entry. Inside the runtime, body content swaps while the navi session persists.

What to build (not a fat flow module)

Flow artifact â€” versioned JSON on hostpark. Route map (HTML paths), entry route, and movement policy (e.g. on miss, offer choices; do not auto-create).

HTML pages â€” one document per screen in ui/ on hostpark.

Manager â€” thin navi helper. Loads the active flow artifact from config, navigates via navi.mod.surf.surf(url) (fetch + replaceChildren), calls registry and resting modules. Example: go("folder") surfs to the folder route from the artifact. Pages use navi in the shell (same window after swap).

Resting modules â€” capability only. Folder, create, capture, numpad helpers. Invoked when needed; they do not orchestrate the journey.

Bootstrap â€” init_script or a small mod ensures registry, Manager, and deps are mounted after reload.

Example artifact sketch (not final):


    {
      "id": "clinic_numpad_direct",
      "entry": "numpad",
      "routes": {
        "splash": "/opry/devops/clinicnotes/ui/splash.html",
        "numpad": "/opry/devops/clinicnotes/ui/numpad.html",
        "result": "/opry/devops/clinicnotes/ui/result.html",
        "folder": "/opry/devops/clinicnotes/ui/folder.html",
        "create": "/opry/devops/clinicnotes/ui/create.html"
      }
    }

State can live on navi between pages when a specific implementation needs it. That is a per-project choice, not a required framework. Owner data stays in registry keys.

Ethos

  1. Modules do not orchestrate UX. Resting modules provide capability. The Manager (driven by flow artifact policy) decides what happens next.
  2. Lower layers keep a voice. Registry lookup/create; pages render; none auto-open because of events alone.
  3. No presumptive auto-reaction. Result page offers Try again / Create / Cancel. Create runs only when the user chooses.
  4. Tools rest. Manager moves. Logic stays dumb about the journey.

Anti-patterns: fat clinicnotes_flow.js with all HTML in JS; event spaghetti where folder listens for owner_found and create listens for owner_missing.

Multiple flow artifacts as variance records

Use separate flow artifact files to record alternative journey designs, even when divergence is small (e.g. splash entry vs direct numpad entry).

Rationale:

  • Each artifact is a named, versioned document of how movement was decided at a point in time.
  • Comparing two artifacts (e.g. clinic_numpad_direct.json vs clinic_numpad_splash.json) shows exactly where responsibility diverged â€” usually entry and one transition, sometimes more later.
  • Alternatives stay published on hostpark and remain switchable without rewriting code.
  • You ship one active flow per deployment; the others are preserved design options, not dead code.

Project config.json (or equivalent) declares which flow artifact is active:


    {
      "flow_artifact": "opry/devops/clinicnotes/flow/clinic_numpad_direct.json"
    }

Manager loads whatever config points at. Changing the shipped experience is a config change (and maybe init_script default route), not a fork of registry or resting modules.

Longer term: maintain a catalog of alternatives at each decision level (flow, schema shape, module split). Only one is active per environment; the rest document variance and stay usable if priorities change.

This is intentional design archaeology â€” not duplication for its own sake, and not a reason to build a generic flow engine early. Each artifact stays concrete and readable.

"Defer a generic flow engine" still applies: no abstract rules interpreter on day one. Add another JSON file when a new journey or entry variant is worth recording.

A hostpark route can be the entry URL while config selects the flow artifact.

Fragment page pattern

HTML fragments are what surf loads into the shell. Navi is in the same window â€” pages call navi directly. Inline script may invoke Manager or a resting module. init_script re-mounts deps after reload.

Fragments or heavier SPA patterns are fine at higher UX spectrum levels when needed. surf is the default in-app navigation tool; HTMX may still bootstrap first paint on entry.

Domain modeling: derived vs stored fields

When a UI artifact encodes information already in another field, derive it. Do not store redundantly.

Example (clinicnotes): each numpad digit has a fixed color. Store code only; map digits via digit_colors.json.

Create-record flows

When lookup can miss, the Manager introduces create as an option â€” not an automatic next step. Prefill code when user chooses create. Collect owner name and pets. Seed dummy defaults for demo usability.
