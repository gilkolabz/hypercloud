Navi module writer’s guide (today)

How to write a navi module for current navi_shell (browser foobarch host + native). This replaces older guides that assumed automatic callin listeners, navi.core, path-derived module names, navi:mod: parks, and storage as plain key bags.

Shell overview: navi shell. Units / entry-plug: navi units.

What a module is

A module is JS with export const register = (navi) => { … return moduleObject }.

Mount loads the source, calls register(navi), and places the return value at navi.mod..

Park tip for a module is a bare single-segment ib matching register().name (e.g. stagedir), optionally with a short hostpark alias (underscore about.name). navi:mod is only the registration ledger (parks[] with ib^gib) — never the module park itself. Declare both method.GET and method.POST as kind: "mod" (usually identical), with rel8ns.bin + content_type: application/navi-module for provision. Host pin: Accept: application/navi-mod → multipart eframe+bin; tip-only Accept: application/eframe; raw bytes Accept: application/navi-module. URL park uses GET callin; navi('…') uses POST callin — same resolution otherwise. Capture uses park: "capture". See README — Park frames: GET vs POST and navi_park_addressing.md.

For request bodies / headers (CRUD, large text), read navi.callinRequest while your command runs — not a relay-specific API. Relay is callin with viaRelay: true.


    export const register = (navi) => {
      const isBrowser =
        typeof window !== "undefined" && typeof window.document !== "undefined";
    
      const eventListeners = [];
      const createdElements = [];
      const timers = [];
    
      const runHelp = async (...args) => {
        if (!args.length || args[0] === "help") {
          return "my_mod — try: my_mod ping";
        }
        if (args[0] === "ping") return "pong";
        return `unknown: ${args[0]}`;
      };
    
      return {
        name: "my_mod", // required — navi.mod.my_mod + park tip navi:my_mod
        version: "1.0.0",
        description: "Example module",
        moduleInfo: {
          name: "my_mod",
          version: "1.0.0",
          description: "Example module",
        },
        commands: {
          // callin verbs — keys are what users type
          my_mod: {
            name: "my_mod",
            description: "my_mod help | ping",
            execute: runHelp,
          },
        },
        onMount: async () => {
          /* optional init */
        },
        onUnmount: () => {
          for (const { element, event, handler } of eventListeners) {
            element.removeEventListener(event, handler);
          }
          eventListeners.length = 0;
          for (const el of createdElements) el.remove();
          createdElements.length = 0;
          for (const t of timers) clearTimeout(t);
          timers.length = 0;
        },
      };
    };

Required for a healthy mount:

  • name — Registry key + park tip navi:. Taken from the live register() return (required). Single segment only (no / or :).
  • commands — Map of command keys → { name, description?, execute }. Must include commands.<name> (the help verb below), including plugin-only mods (stagejockey plugins, supermouse plugins) that have nothing else to type. Other keys are only reachable as <name> <key> …, never as a first word.
  • onUnmount — Clean DOM / listeners / timers you added (browser).

Help text (required)

Every module answers navi('<name>') and navi('<name> help') with help text written by hand for that module. Typing a mounted mod's name with no commands.<name> throws navi.mod.<name>.commands.<name> not available, so plugin-only mods are not exempt.

  • Key it as commands.<name> (same string as the module name); no args and help both return the text.
  • Write it for a person who just mounted the mod: what it is for, how to use it (for jockey plugins, which claims appear, on what, and in which direction), what else must be mounted, and any subcommands.
  • Do not generate it from description, claim ids, or Object.keys(commands), and do not return only a version string.
  • Live state is welcome after the text, but the hand-written part must still read correctly when nothing else is mounted.
  • Keep it plain text, a few short lines, no ANSI.
  • Do not store module state on the same tip ib as the module park (<name> / navi:<name>). That shadows the park; a bare navi('<name>') then returns the state frame instead of help. Use a nested ib (e.g. navi:<name>:frame) or navi.storage.item.
const HELP = [
  "image_resize — resize a picture on the page by dragging.",
  "use: select an image with stagejockey → +1 \"image-resize\"; drag a corner,",
  "     click inside the frame to keep it, Escape / click outside to undo.",
  "needs: stagejockey",
].join("\n");

commands: {
  image_resize: { name: "image_resize", description: "help", execute: async () => HELP },
},

MIME for published bytes: application/navi-module.

Install / mount


    mount stagedir

(Fetch route / filename need not match register().name — that module plants park tip navi:stagedir.)

Surf flow (simplified):

  1. Fetch route as a navi module.
  2. mount(source) → register(navi) → live moduleObject.name.
  3. plantModulePark under that live name → tip navi: + bin (kind: "mod"). The fetch route is not the park ib.
  4. Index navi:mod.parks[] with live Object.keys(commands) (may be []) and mut8 the tip’s method.GET.commands / method.POST.commands when the mod has more than one verb. Claim the mount on this instance’s unit tip when units are active.

Name comes from the register return, not a source scrape (scraping false-positives like WebCrypto { name: "Ed25519" }).

Also: mount navi:my_mod when the park tip already exists; navi.remount() mounts every park listed on ledger navi:mod, independent of which unit this instance is.

Do not hand-register navi.on('callin', …) for your verbs. Hard park dispatch owns callin.

Callin discovery (parks, not a flat command registry)


    navi('my_mod ping')
  1. First token → park tip navi: (modules and surf included). Shell/kernel tips also use flat navi: (storage, init_script, mod, plug, reseed, …). There is no navi:mod: park path.
  2. Optional unit prefix first: navi('unit/01/my_mod …') — see navi_units.html.
  3. If that tip is missing, search mounted parks for a command key equal to the token (findMountedCommand).
  4. Tip must be listed on navi:mod.parks and http.POST.kind === 'mod' for callin (URL GET uses http.GET).
  5. Execute navi.mod..commands..execute(...rest).

So callin is park + command key, not “whatever string you hope is global.”

Namespace coherency (incidental, but aim for it)

Callin discovery does not demand that:

  • module name,
  • park tip leaf (navi:),
  • and every commands key

are the same string. Those are separate fields. Matching them is incidental hygiene, not a runtime rule.

In practice the mount snapshot (navi:mod.parks[].commands + tip method.GET.commands when multi-verb) should list the verbs people type. Single-command mod parks use method.GET.command only.

  • navi('my_mod …') hits tip navi:my_mod, and
  • commands.my_mod exists as the default verb.

When a short alias is nicer to type, alias both keys to the same execute so tip name and short verb both work. Example: stagedir ships:


    commands: {
      stagedir: { name: "stagedir", execute: runStagedir },
      horizon_stagedir: { name: "horizon_stagedir", execute: runStagedir },
    }

Park tip / navi.mod key is stagedir (navi:stagedir). Users can type stagedir show or horizon_stagedir show when both keys are listed on the tip and ledger.

Anti-pattern: name: "stagedir" but only commands.stagedir, with a planted tip listing ["horizon_stagedir"] only. Then horizon_stagedir callin will not resolve under park dispatch.

Snapshot timing: index/tip commands are written at mount from commands{}. Mutating commands later on the live object does not update discovery until remount / navi('reindex'). Programmatic navi.mod.x.commands.y.execute() still works without remount.

Storage (tip + bin; item/file are shims)

Authoritative space is tips + bins (tip pointer + tip.frame at ib^gib). navi.storage.item / file remain as shims; bare keys presume navi: (no bare ↔ navi: bridge on lookup).

  • Prefer tip frames + rel8ns.bin for module-owned data when you care about the ledger.
  • Park-check / surf paths do not presume: surf horizon/enter is host; surf navi/horizon/enter is local tip space.
  • Path GET for modules: navi.fetch(path) (optional). Global fetch still works in the browser via the SW.

See also: navi shell storage, and manifest.

Paying for foobarch writes (navi.tokens)

Foobarch commits need a usage token (X-Foobarch-Usage-Token). Do not keep a private token list in your mod; use the shared stash (local tip tokens, keyed by origin):


    const token = await navi.tokens.take(host);   // throws err.code "NO_TOKENS" when empty
    // … PUT with the token …
    // on failure, unless the host said "consumed" / "invalid usage token":
    await navi.tokens.giveBack(host, token);

Also count(host), look(host), add(host, tokens), and an optional path argument for a separate budget. The host only spends a token when the commit is saved. Users fill the stash via hypertext/intro; operators via relay tokens add|file. Full guide: foobarch-usage-budgets.

Units (when you care about multi-instance)

Registration (navi:mod) ≠ session claim on this window’s unit. Prefer reading navi_units.html before gating destructive ops. Permission-style APIs (storage kill, prune, …) expect a bonded entry-plug and usually a confirm (via entry-plug of ).

Browser vs native

  • DOM / window — Browser: yes. Native (navi_shell.exe / navi_shell-linux-x64 / Node): no — guard with isBrowser.
  • navi.require('fs') etc. — Browser: no. Native: yes (native modules).
  • Ports / SQLite hosts — Browser: N/A. Native: e.g. hostparkinator_5000.

One register can serve both; throw or no-op when the environment is wrong.

Service worker (optional)

  • Shell registers /sw.js.
  • Page: navi.sw.on(name, fn), navi.sw.registerPlugin….
  • Clear handlers in onUnmount (owner-scoped).

PWA identity: prefer same-origin /manifest.json (host tip or SW overlay from navi.pwa.set). Do not rely on blob: manifests for Chromium installability. Icon src must be fetchable http(s) paths.

Offline boot: SW caches start_url document + /navi_shell.js (navi.pwa.shell.*). Tip/bin localpark still needs the runtime loaded first.

Cleanup

Track what you add; tear it down in onUnmount: listeners, DOM nodes, style tags, observers, timers, navi.sw handlers. Unmount without cleanup leaks across remounts in a long-lived tab.

Publishing

A published module is a hostpark route whose bin is the module source (application/navi-module) and whose frame says kind: "mod". The short park name is what mount fetches. After mount, the live park tip is navi:<name> from register(), which can differ from the route you fetched.

Warez is the catalog card for that route: about.name matches the live register() name, about.version matches the source version, and about.commit-devnote is one sentence on why this generation exists. Mount with mount/<park>.

Quick checklist

  • [ ] Foobarch writes pay via navi.tokens (no private token stash; refund unless the host says consumed/invalid)
  • [ ] export const register
  • [ ] name in return (and usually moduleInfo) — single segment
  • [ ] Park tip will be navi: (not navi:mod:)
  • [ ] commands with execute if you want callin; omit / empty OK for plugin-only
  • [ ] Prefer commands. === module name; add aliases if you want short verbs
  • [ ] Park tip name comes from live register() return — keep name accurate there
  • [ ] onUnmount cleans browser side effects
  • [ ] Do not attach your own top-level callin listener for verbs
  • [ ] After changing commands{}, remount (or reindex) so discovery snapshots update
