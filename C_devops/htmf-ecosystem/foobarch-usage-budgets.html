Foobarch usage tokens and budgets

Usage tokens are one-shot write tickets for foobarch (hostparkinator_5000). A mint batch is one budget (shared lead on every token). Navis keep header tokens in a local stash (navi.tokens); tips can also carry or point at a reserve so clients write without holding a token.

What costs a token

  • Commit / tombstone on foobarch (PUT, PATCH, any tip-declared commit/tombstone): one token, unless the tip pays from a reserve.
  • relay connect: one token per WebSocket connection. Host restarts and remount_host drop sockets, so each relayed navi pays again on reconnect.
  • Free: reads, and HTTP callins through relay parks.

The navi stash (navi.tokens)

Local tip tokens: data.hosts[origin].unused (one token per line), optional paths[path].unused sub-budgets. Calls are serialized; host defaults to the relay host, else navi.origin.

await navi.tokens.count(host?, path?)
await navi.tokens.look(host?, path?)              // first token, kept
await navi.tokens.take(host?, path?)              // first token, removed; throws err.code "NO_TOKENS" when empty
await navi.tokens.giveBack(host, token, path?)    // refund
await navi.tokens.add(host, tokens, path?)        // array or whitespace string → { added, count }

Filling it: users request tokens on hypertext/intro (Approver approves, tokens are claimed into the stash). Operators: relay tokens add <token…>, relay tokens file <path> (delete the file after), relay tokens for the count.

Spend pattern for mods

The host consumes a token only after the commit is saved. Refusals (bad envelope, policy or genesis-gate denial, stale parent) spend nothing. The token is dead only on 401 invalid usage token or 403 usage token already consumed.

const token = await navi.tokens.take(host);
let res, text;
try {
  res = await fetch(`${host}/${ib}`, { method: "PUT", headers: { "Content-Type": "application/json", "X-Foobarch-Usage-Token": token, ...signHeaders }, body });
  text = await res.text();
} catch (e) {
  await navi.tokens.giveBack(host, token);
  throw e;
}
if (!res.ok) {
  if (!/consumed|invalid usage token/i.test(text)) await navi.tokens.giveBack(host, token);
  throw new Error(`PUT ${ib} → ${res.status}: ${text.slice(0, 300)}`);
}

Keep tokens in navi.tokens. Leave the mint password with the operator. Never print whole tokens; the 16-hex lead is fine for logs.

Mint shape

Mint N tokens → one shared 16-hex lead + unique 48-hex suffix each (64 hex). Response { tokens }; lead = tokens[i].slice(0, 16). Operator only.

POST /foobarch/tokens
X-Foobarch-Usage-Password: …
{"count": N}

Mutation payment (precedence)

For commit / tombstone kinds (any verb). Reads unpaid.

  1. X-Foobarch-Usage-Token if present
  2. else data.foobarch.tokens on that tip (the new frame drops the head token)
  3. else rel8ns["foobarch.token_reserve"] / data.foobarch.token_reserve: spend two from the reserve (content mut8 + host index mut8)

Naive clients can use a tip that already links a reserve and never see a usage token.

Product pattern (reserves)

  1. Mint a budget (one lead).
  2. Park a reserve tip under an obscure ib; store tokens in data.foobarch.tokens.
  3. Hand the operator the reserve ib (or a bootstrap tip that links it), not the usage password.
  4. Work frames rel8ns to that reserve; clients mut8 frames; the budget depletes on the reserve.
  5. Refill by mint + append. A proxy for realtime is optional later; tip lineage is enough for v1 shared state.

Do not publish reserve ibs on public catalogs. Different roles/products → different reserves / leads.
