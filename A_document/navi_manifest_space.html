navi manifest space

Design note: make navi_shell local storage and callins symmetrical with foobarch_host tips — one vocabulary on both ends. Experiment behind versioned navi_shell.js on the host. This file is meant to be readable in a text editor.

Units / multi-instance tip space: navi_units.html.

1. Where we are

Today the host and the shell speak different dialects:

  • foobarch_host — tips are ibgib frames with park + data.method[METHOD].kind, optional bin bytes, soft tombstone vs admin hard-delete.
  • navi_shell — navi.storage.item / navi.storage.file key bags; callins as a parallel command registry; navi.mod.* as live JS objects after mount.

Tiny, orient, surf, snoopy, and jockey live-state all invent their own key shapes on top of that bag. The spaghetti is the missing shared tip model.

2. Where we are going

Local navi becomes a miniature foobarch space:

  • Every stored tip is a manifest (expanded sense — see §3).
  • Method controls (GET / PUT / POST / DELETE / …) describe what the tip does, including a sync/async preference.
  • Opaque bytes live in a bin relation (replaces item/file dialectic).
  • Callins are parks under navi/. The callin language presumes that prefix: navi("surf …") addresses tip navi/surf; remainder is passthrough. Same remainder / capture / defer ideas as the host.
  • Admin always wins locally (user can wipe or rewrite any tip); policies under that are optional later.
  • Wire upgrade: host ↔ shell may pass ibgib / manifest envelopes when both sides opt in; raw byte proxy stays valid.
foobarch_host                          navi_shell (local)
─────────────────                      ─────────────────
tip ib                                 tip ib  (navi/…, tiny/…, …)
ibgib frame                            ibgib frame
data.method[METHOD]                      data.method[METHOD]
rel8ns.bin / bin table                 local bin store
park + remainder                       callin park under navi/
admin hard-delete                      navi admin (user)

3. Semantic shift: manifest = frame contract (not “proposal”)

Stop saying proposal for the parked tip shape. Let manifest mean the contract in an ibgib frame’s data: normative controls (method, optional park), metadata (about), and associated-data notes — the thing you GET when you ask what a route is and how to use it. Canonical vocabulary: A_document/manifest.md.

The stored unit is always an ibgib frame { ib, gib, data, rel8ns }. Tip-level parts tags such as ibgib_frame, json, and network_proposal are deprecated noise in new writing (implied by being a JSON frame, or legacy host labels). Live tips may still carry them until migrated.

Optional single-field route claim (not addressability — an ib is already addressable): 

"park": "capture" | "defer"   // omit = not in path/callin resolve

READMEs and foobarch_host commentary should migrate language from “proposal” to “manifest” as we touch them. Code identifiers may lag; docs lead.

4. Edges (answered so far)

4.1 Bootstrap / seed

navi_shell.js seeds like init_script and mod:surf.js today: plant a small set of tip frames into local space on first run (or when missing). We author those seed manifests here in repo, bake or fetch them into the shell, then runtime only mut8s them.

Minimum seed set (v0) — authored under C_devops/navi_redux/seed/:

  • navi — root park: what navi/ means; links to children.
  • navi/mod — index manifest of mounted parks (updated on mount/unmount).
  • navi/admin — user-level hard controls (delete tip, reseed, …).
  • navi/init_script — boot command list (replaces storage key init_script).
  • navi/surf — first real callin park (pilot).

See C_devops/navi_redux/README.html. Exact frames live as *.frame.json there; gibs are placeholders until plant content-addresses.

4.2 Sync vs async

Each method control may declare preference, e.g.: 

"GET":  { "kind": "bin",    "mode": "sync" }
"PUT":  { "kind": "commit", "mode": "async" }
"POST": { "kind": "lua",    "mode": "async" }

Default if omitted: sync for local bin/frame reads; async for commit / cross-host / SW-bridged work. Callers that need a promise always may still await; sync controls must not rely on microtasks to finish.

4.3 Is every navi.* a park? Can JSON equal the live object?

Directionally yes: navi.mod ↔ navi/mod, navi.surf ↔ navi/surf. Devtools and parks share one addressing story.

Coherence rule (important):

  • The manifest tip is the normative, serializable description (controls, subcommands, where the module bytes live, sync prefs).
  • The live JS object (navi.mod.surf) is the runtime projection after mount — not something we fully reify as JSON.
  • navi/mod index lists parks that are mounted (ib, name, subcommand list, optional subject addr). It does not deep-clone the module export.

So: you can express what would be true if you referenced the mod (name, commands, park path, kinds) in JSON. You cannot honestly serialize closures / DOM handles into the tip. Overlap is coherent if we treat the tip as the contract and the object as the fulfillment.

4.4 Who may park

  • Only while mounted.
  • Only parks that correspond to real module commands / subcommands the module declares (keep subcommand tables on mods).
  • On mount: module registers parks; shell recommits navi/mod index (mut8) so registration is visible as data, not only as side effect.
  • Internal pointing (park → another park / remainder handoff) should mirror host redirect/proxy kinds once we need it.

Unmount removes or tombstones that module’s parks and mut8s the index again.

4.5 Remainder / capture / defer

Reuse host ideas: a single park field ("capture" | "defer"; omit = not in resolve). Do not author boolean park, park_precedence, or park_depth — migrate live tips first. Exact client subset TBD while surfing the pilot — do not invent a third dialect. Admin permission for mods to use admin APIs is user-gated; tip-level policies under admin are later (same shape as host, no examples required yet).

4.6 Wire upgrade

Ibgib frame is the stored unit on foobarch; the manifest lives inside / as that frame’s data (and rel8ns). Both ends should learn:

  • Request: optional desire for frame/manifest (header or query).
  • Response: either raw bytes (today) or frame JSON with bin out-of-line / embedded per control.

Passing ibgibs as the language makes snoopy, gibbert, tiny, and potter the same family of consumers.

5. Admin vs method DELETE (keep the host split)

  • Method DELETE on a tip — whatever data.method.DELETE.kind says (tombstone, proxy, …).
  • Admin delete — hard wipe of local tip/frames/bins for that ib, always available to the user (and to mods only if permitted).

6. Practical path (strategic)

  1. Note + vocabulary — this document; light updates to manifest.md / host README language over time.
  2. Seed manifests — hand-author navi, navi/mod, navi/surf, navi/admin fixtures; shell loads them like init_script / surf module seed.
  3. Local resolve stub — minimal resolveRoute + httpControl over a tip+bin store (IndexedDB), enough for GET frame/bin and admin delete. Do not migrate all of storage.item yet.
  4. Surf pilot — hard callin: space is presumed under navi/, so navi("surf …") → tip navi/surf + remainder passthrough via http[default_method] kind:mod. Mount mut8s navi/mod; auto-plants navi/<name> if missing. No registry fallback.
  5. Widen — potter, snoopy, tiny as tips; retire item/file for new code; optional host Accept-frame.

Pilot success criteria: from a clean shell, seed tips exist; mounting surf updates navi/mod; invoking surf via park/callin uses method controls; user can admin-delete and reseed.

7. Seed tip sketch (surf-first)

Illustrative controls — canonical seed frames are in C_devops/navi_redux/seed/ (including navi/init_script). 

navi/surf tip (conceptual)
{
  "ib": "navi/surf",
  "gib": "<content-addressed>",
  "data": {
    "park": "capture",
    "default_method": "GET",
    "method": {
      "GET":  {
        "kind": "mod",
        "target": "surf",
        "command": "surf",
        "mode": "sync",
        "commands": ["surf", "surf_settings"]
      },
      "POST": {
        "kind": "mod",
        "target": "surf",
        "command": "surf",
        "mode": "async",
        "commands": ["surf", "surf_settings"]
      }
    },
    "module": {
      "name": "surf",
      "subject_seed": "bin "
    },
    "about": {
      "label": "surf",
      "description": "surf mod park"
    },
    "n": 0,
    "timestamp": "…"
  },
  "rel8ns": {
    "past": [],
    "tjp": [],
    "dna": []
  }
}

navi/mod index (conceptual)
{
  "ib": "navi/mod",
  "data": {
    "park": "capture",
    "method": {
      "GET": { "kind": "frame", "mode": "sync" }
    },
    "about": {
      "description": "registration ledger"
    },
    "parks": [
      { "ib": "navi/surf", "name": "surf", "commands": ["surf"] }
    ]
  }
}

kind: "mod" means: dispatch remainder + body to the mounted module named by target (live object), after checking the subcommand is listed on the tip / module.

8. Scale in view (storage + props)

Callin parks are the thin end of a thicker wedge: local navi is meant to look like foobarch’s tip+bin+http model, not like a bag of ad-hoc IndexedDB keys.

  • Near: callins under navi/; navi/mod ledger; seeds; dedicated IndexedDB tips/bins (ib as tip key).
  • Next: remaining navi.storage.item/file call sites (settings, SW paths, third-party mods) move to tip/bin or disappear.
  • Directionally: live props and parks share ibs — navi.storage, navi.mod, even future navi.sw surfaces resolve through the same park/method grammar (GET frame/bin, PUT commit, DELETE tombstone/admin). Devtools “dot path” and URL/callin path are two spellings of one space.
  • Host side: foobarch route tips are the same manifest-frame shape (e.g. tip navi_shell.js + bin) — network twin of a local tip. Legacy parts tails on those tips are noise to strip over time.

Pilot discipline: hard callin first (no registry fallback). Storage generalization follows once tip+bin stores exist and call sites move; do not pretend item keys are parks until resolve is real.

9. Non-goals (for now)

  • Full rename of every “proposal” string in foobarch_host source.
  • Mass-stripping legacy parts / boolean park from every live tip in one pass.
  • Replacing tiny’s space in the same pass as surf.
  • Mandatory frame responses on all host routes.

10. Open questions

  • Whether tip-level parts stay at all (optional labels) vs stage occupant typing — see manifest.md.
  • Whether navi.storage.item.get becomes a compatibility shim over tip GET or stays until call sites move.
  • How SW plugins (snoopy) record against tip ibs vs raw pathnames.
  • Remainder grammar for nested subcommands (navi/surf/foo/bar vs query/body).
